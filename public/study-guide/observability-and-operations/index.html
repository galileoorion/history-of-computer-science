· · Start here

Learning objectives

  1. Explain how observability supports operating a system and distinguish a user-visible failure from a healthy-looking component.
  2. Define a service level indicator, a service level objective, and an error budget for a named user journey, then calculate the budget from traffic and target.
  3. Choose metrics, structured logs, and distributed traces to answer different diagnostic questions across a request path.
  4. Design a telemetry pipeline that preserves useful detail while controlling label cardinality, sampling, retention, and sensitive data.
  5. Choose actionable alerts, external checks, health probes, and runbooks that connect a detected problem to a response.
  6. Compare staged release methods and plan compatible configuration and schema changes that can be reversed safely.
  7. Use capacity tests, recovery objectives, and restoration drills to verify that operational promises are achievable.

§1 · Definitions

Core concepts

This section defines observability, operations, telemetry, and a user journey. These terms connect system signals to the outcomes that users actually experience.

Definition

Observability The ability to infer a system's internal behaviour from its outputs well enough to explain an unexpected state or failure.

Definition

Operations The continuing work of measuring, changing, protecting, and restoring a running system so its stated behaviour remains dependable.

Definition

Telemetry Measurements and event records emitted by software and infrastructure, commonly as metrics, logs, and traces.

Definition

User journey A sequence of actions that delivers a user outcome, such as finding a product and placing an order, potentially across several services.

A design becomes observable when the signals let an operator connect an affected journey to the component or data transition responsible for it. Operations then uses that evidence to choose an action: stop a rollout, reduce admission, repair an integration, or restore data. A component's CPU graph can be normal while an order is paid but never confirmed, so operational design must start from the required outcome and trace inward to the resources that support it.

The common confusion is to equate observability with collecting every possible log. Large volumes of records can still leave a failure unexplained if they lack a shared request identity, omit the decisive state transition, or measure only internal health. Useful signals answer a question and lead to an action; collection volume alone does neither.

§2 · Outcomes and targets

Define outcomes and reliability targets

Definition

Service level indicator (SLI) A measured quantity that represents a defined aspect of service behaviour, such as the fraction of eligible requests that complete correctly within a latency limit.

Definition

Service level objective (SLO) A target for an SLI over a stated measurement window.

Definition

Error budget The permitted number or fraction of events that may fail an SLO's good-event rule within its measurement window.

An SLI needs a population and a good-event rule. For checkout, a good event might mean that an eligible attempt reaches a durable order confirmation within a stated duration; merely returning HTTP 200 would not prove that the order exists. The measurement point matters too. A server-side SLI can miss failures at the edge or in a client, while a scheduled test journey can cover only the path it exercises. Define exclusions narrowly so a dependency outage is not hidden by removing its failed requests from the denominator.

The diagram shows how the outcome rule is applied before the target is evaluated.

Read left to right: first decide which attempts count, then classify each result, then aggregate over the same window used by the objective. A service dashboard can display the resulting ratio, but the rule that classifies an event must be specified before the dashboard is trusted.

Worked examplea request-based error budget

Consider an API with 50 million eligible requests in a 30-day window and an SLO that 99.9% are good. The allowed bad fraction is 1 − 0.999 = 0.001. The error budget is 50,000,000 × 0.001 = 50,000 bad requests. Check: 50,000,000 − 50,000 = 49,950,000 good requests, and 49,950,000 ÷ 50,000,000 = 0.999.

Assume 20,000 bad requests have already occurred in that window. The spent share is 20,000 ÷ 50,000 = 0.40, or 40%, leaving 50,000 − 20,000 = 30,000 bad requests before the target is missed. This arithmetic is specific to a request-based SLI; a time-based availability objective needs a time denominator instead.

§3 · Diagnostic signals

Connect metrics, logs, and traces to the request path

Definition

Metric A numerical measurement aggregated over time, such as request rate, error count, queue age, or connection-pool saturation.

Definition

Structured log An event record with named fields that can be searched and correlated without parsing free-form prose.

Definition

Distributed trace A record of one operation's path through services, made of timed spans that represent individual units of work.

Definition

Correlation ID An identifier carried across requests, events, logs, and traces so records belonging to one logical operation can be joined.

Definition

Tail latency Response time at a high percentile, such as the 99th percentile, that exposes slow requests hidden by an average.

Metrics show whether a problem is widespread and when it began. Logs explain discrete decisions and failures, such as a payment result being marked unknown. A trace shows where one slow or failed request spent time across the dependency graph. The correlation ID joins these views. Instrument entry points and asynchronous handoffs so the ID survives a queue; record the outcome of important state transitions, not only incoming requests.

This comparison helps select the signal that answers a particular question.

Signal Question it answers well Limitation to plan for
Metric How often and how broadly is a condition occurring? Aggregation can hide one affected key or one incorrect transition.
Structured log What decision or state change occurred for this operation? Searching high-volume records can be expensive and slow.
Distributed trace Which calls and waits shaped this operation's latency? Sampling may omit the particular failed request.

The signals complement rather than replace one another. A rising checkout tail latency can lead to a trace of a slow database call, then to a log explaining which lock or query failed; the metric still shows whether the issue affects all checkouts or one route.

The diagram follows a request and its identifiers through two services and a queue.

Follow the top line for synchronous calls and the lower line for delayed work. The queued event carries the correlation ID because a later worker is part of the same logical journey even though it runs in a different process and at a different time.

A high percentile should be calculated from the combined request distribution for the chosen window. Averaging the p99 values of individual hosts does not produce a fleet p99, because each host may have different traffic volume and latency shape.

§4 · Telemetry design

Keep the telemetry pipeline useful and affordable

Definition

Metric label A named dimension attached to a metric series, such as route, status class, or region, that permits filtering and grouping.

Definition

Cardinality The number of distinct values or combinations a label set can take, which determines how many separate time series must be stored.

Definition

Sampling Keeping a selected subset of high-volume telemetry, often traces or logs, while preserving a defined basis for interpretation.

Definition

Retention The period for which collected telemetry remains available before it is deleted or moved to cheaper storage.

Instrumentation sends events through collectors and processing stages to storage. This path has its own failure modes: buffers can fill, sampling can discard the only evidence of a rare event, and high-cardinality labels can overwhelm a metrics store. Keep labels bounded, reserve request IDs for logs and traces rather than metric labels, and choose a retention period from diagnosis and audit needs. Avoid putting secrets or personal data into telemetry; access and deletion rules apply to these stores as well as to primary data.

The diagram shows where volume and privacy controls belong.

Read left to right: the service emits the evidence, the collector limits and routes it, and each store keeps only what its use requires. If this pipeline fails, the service should have a defined behaviour, and loss of operational evidence should itself be visible through an independent signal.

Worked examplelabel combinations

Consider a request metric labeled by 3 methods, 5 routes, 4 status classes, and 10 instances. Assume every combination occurs. Its upper-bound series count is 3 × 5 × 4 × 10 = 600. If a user identifier with 100,000 distinct values is added and, as a worst-case assumption, each user occurs in every existing combination, the bound becomes 600 × 100,000 = 60,000,000 series. Check: the new dimension multiplies the original count by 60,000,000 ÷ 600 = 100,000. Real counts depend on which combinations occur, but a per-user metric label is still an unbounded growth path; put the identifier in a protected log or trace field when it is genuinely needed.

§5 · Detection and response

Detect problems and make alerts actionable

Definition

Synthetic monitoring Scheduled execution of a controlled user journey from outside the service to check a critical path even when real traffic is absent.

Definition

Invariant alert An alert on a condition that must hold in the system's data or workflow, such as every paid order eventually reaching a terminal state.

Definition

Health check A probe that reports whether an instance is running or able to receive traffic; liveness governs restarting it, while readiness governs routing new work to it.

Definition

Runbook A maintained procedure linked to an alert that describes how to confirm, contain, repair, and verify a specific failure.

Definition

Burn rate The rate at which an SLO's error budget is being consumed relative to the rate that would use the whole budget evenly over the window.

An alert should identify an actionable condition, an owner, and a response. User-visible errors, sustained SLO burn, and broken invariants are stronger paging signals than an isolated CPU threshold. Resource saturation remains useful for diagnosis and capacity planning. A synthetic journey catches a failed path at low traffic and can cover the public edge; it must use safe test data and be excluded from business volume. Liveness probes should not restart every instance because one shared database is slow, and readiness should answer whether an instance can usefully accept traffic rather than test every possible dependency.

The diagram connects detection to response and verification.

Read the top line as the detection path. The lower loop closes only when the operator confirms the user outcome has recovered and updates the runbook or instrumentation so the next incident is easier to diagnose.

Worked exampleinterpreting error-budget burn

Consider a 99.9% request-success SLO. Its allowed bad fraction is 1 − 0.999 = 0.001, or 0.1%. Assume a recent interval has 10,000 eligible requests and 100 bad results, so the observed bad fraction is 100 ÷ 10,000 = 0.01, or 1%. The burn rate is 0.01 ÷ 0.001 = 10. Check: 1% is ten times 0.1%.

If the request rate and bad fraction remain constant, a fresh 30-day budget would be consumed in 30 ÷ 10 = 3 days. This is a projection under the constant-rate assumption, not a promise about how much budget remains now. An alert can use burn measured over more than one window so a brief spike and a sustained failure are treated differently.

§6 · Change safety

Release and change the system safely

Definition

Canary release A rollout that directs a small, measured share of traffic to a new version before widening exposure if its outcomes remain acceptable.

Definition

Rolling deployment Replacement of running instances in batches so old and new versions coexist temporarily.

Definition

Blue-green deployment Keeping an old and a new environment ready, then switching the chosen traffic route between them, usually for a rapid reversal if needed.

Definition

Feature flag A runtime control that changes a code path without a new deployment; a kill switch is a flag reserved for quickly disabling risky behaviour.

Definition

Infrastructure as code Version-controlled definitions of infrastructure and configuration that can be reviewed and applied reproducibly.

Definition

Expand–migrate–contract A compatible sequence for changing stored data: add the new structure, move data and readers while old and new versions coexist, then remove the old structure in a later step.

Release design is part of operations because a bad change can affect every healthy component at once. A canary limits initial exposure and compares user outcomes, latency, and correctness signals with the old version. A rolling deployment limits how many instances are replaced together but still requires old and new code to share data safely. Blue-green can make traffic reversal quick, but a single switch to all users does not limit the initial blast radius. Feature flags separate deployment from activation; an emergency flag must be reachable when the affected dependency is failing. Infrastructure as code makes the intended environment reviewable, and emergency manual changes must be reconciled back into it.

The diagram shows a staged release with a measured decision before widening traffic.

The two branches see different shares of the same live workload. Compare like-for-like routes and users where possible, and include business outcomes: a version returning HTTP 200 with a missing order is not a successful canary. Schema and message changes need compatibility across both versions; expand–migrate–contract delays irreversible removal until older instances and data are accounted for.

Worked exampleinitial canary exposure

Consider a service receiving 20,000 requests per second. Assume the canary receives exactly 1% for five minutes and every canary request is affected by a new defect. Its rate is 20,000 × 0.01 = 200 requests/s; five minutes is 5 × 60 = 300 s, so at most 200 × 300 = 60,000 requests follow the faulty version during that interval. Check: the full service receives 20,000 × 300 = 6,000,000 requests, and 60,000 ÷ 6,000,000 = 0.01. The cap holds only if routing really stays at 1%, and the defect must produce a signal the comparison can detect before traffic widens.

§7 · Capacity and recovery

Plan capacity and prove recovery

Definition

Capacity planning Estimating future demand and comparing it with measured component limits and the headroom needed for bursts or failures.

Definition

Load test A controlled application of realistic traffic to measure throughput, latency, and failure behaviour at expected and excess load.

Definition

Recovery time objective (RTO) The longest acceptable time from a specified disruption until a required function is restored.

Definition

Recovery point objective (RPO) The greatest acceptable age of recoverable data at the time of a specified disruption, which bounds potential data loss in time.

Definition

Restoration drill A timed exercise that restores retained data into a usable system and checks both completeness and application behaviour.

Operations closes the design loop by comparing actual traffic with the assumptions used to size the system. Forecast peak demand, include work caused by retries and recovery, and load-test the same traffic mix and key skew that production sees. The capacity limit is the rate at which the user-visible target still holds, not the rate at which a process merely remains alive. Keep room for a node or zone loss if that fault is within the availability goal.

Backups and replicas solve different problems. A replica can take traffic after a node failure but also copies a mistaken deletion. A protected backup and retained change history make recovery from corruption possible, while a restoration drill establishes how long it actually takes and which writes survive. RTO and RPO must be stated for a named scenario and compared with measurements from drills, not inferred from the existence of backups.

The diagram shows the operating loop from measurement to verified recovery.

The upper loop revises capacity as demand changes. The lower path tests whether stored recovery material can become a working service within the required time and data-loss bounds.

Worked examplecapacity after one instance fails

Consider a forecast peak of 900 requests per second. Assume a tested instance meets the latency target at no more than 350 requests per second, and assume one instance may fail while the peak continues. With all instances healthy, the arithmetic minimum is ceil(900 ÷ 350) = 3. To keep serving after one fails, provision 3 + 1 = 4 instances. Each of the three survivors then receives 900 ÷ 3 = 300 requests/s, below the tested 350. Check: 3 × 350 = 1,050 requests/s, above the 900 target, whereas two survivors would offer only 2 × 350 = 700 requests/s. This assumes traffic can be redistributed evenly and the shared dependencies can handle the same peak.

· · Review

Common mistakes

The first mistake is defining success as an HTTP 200 response. It happens because server status is easy to count, while completion of a business transition may occur later. Define the good event at the user outcome, including latency and correctness, and measure it from a point that sees the relevant failures.

The second mistake is labeling a metric with a user or request identifier. It happens because the label makes a dashboard filter convenient for one investigation, but it multiplies the number of stored series by a large and growing population. Keep bounded dimensions on metrics and use protected logs or traces for individual identities.

The third mistake is paging on every resource spike or every nonzero invariant count without a response policy. It happens because thresholds are easy to set, but a transient fluctuation or an expected in-flight state may not need a person. Alert on sustained user impact or a genuinely broken invariant, assign an owner, and link a tested runbook.

The fourth mistake is treating a small canary's clean HTTP error rate as proof of a safe release. It happens because the new code may return plausible but incorrect data, or the canary may not exercise the affected route. Compare business outcomes and coverage, and keep old and new data formats compatible until the rollout is complete.

The fifth mistake is treating backups as verified recovery. A snapshot may be unreadable, incomplete, inaccessible during an outage, or too slow to restore. Restore into an isolated environment, check application invariants, and measure the actual RTO and RPO.

· · Exercises

Practice questions

These questions mix recall, calculation and application across the whole guide, and each answer is collapsed beneath its question to be opened once the reader has worked out an answer.

Question 1 · distinction

A checkout alert shows a rising bad-request ratio. What different questions should a metric, a trace, and a structured log answer during diagnosis?

Answer

The metric shows how many eligible checkouts fail, when the increase began, and which bounded route or region dimensions are affected. A trace follows one affected checkout through its services and shows where time or failure occurred. A structured log records the decision or state transition at that point, using the same correlation ID so the event can be tied to the trace and the original request.

Question 2 · calculation

An API receives 8 million eligible requests in a measurement window and has a 99.95% good-request SLO. How many bad requests can it tolerate, and what fraction of the budget has been used after 1,200 bad requests?

Answer

The bad fraction is 1 − 0.9995 = 0.0005. The budget is 8,000,000 × 0.0005 = 4,000 bad requests. After 1,200, the used fraction is 1,200 ÷ 4,000 = 0.30, or 30%; 4,000 − 1,200 = 2,800 remain. Check: 8,000,000 − 4,000 = 7,996,000 good requests, and 7,996,000 ÷ 8,000,000 = 0.9995.

Question 3 · calculation

A metric has 6 route labels, 3 status classes, 4 regions, and 5 instances. Assuming every combination occurs, how many series does it produce? What happens if a label with 20,000 distinct customer IDs is added and every combination occurs?

Answer

The original count is 6 × 3 × 4 × 5 = 360 series. The customer label raises the upper bound to 360 × 20,000 = 7,200,000 series. Check: 7,200,000 ÷ 360 = 20,000, the factor introduced by that label. Actual counts depend on which combinations occur, but the risk follows from the multiplicative bound.

Question 4 · application

A canary returns HTTP 200 and has normal latency, but some orders are missing their confirmation event. Which release signals and response should change?

Answer

Count durable order confirmations and missing confirmation events as outcome or invariant signals, segmented by version so the canary can be compared with the old version. Stop widening the canary and route its traffic back if the missing-event condition is confirmed. Preserve the event records or repair path needed to reconcile affected orders, and do not remove old schema or message support until both versions and the backlog are accounted for.

Question 5 · open-ended

An online shop expects a seasonal traffic peak, sometimes loses its recommendations service, and needs to deploy a new order schema without stopping checkout. Describe the observability, alerting, rollout, capacity, and recovery decisions that should be made together.

Answer

Define good checkout and browsing events, their measurement window, and the permitted bad-event budget. Emit request rate, error and duration metrics; bounded resource saturation metrics; a correlated trace across checkout; and structured logs for order state changes. Alert on user impact and broken order invariants, with an owner and a runbook. Keep recommendations optional with a visible fallback signal, and test the missing dependency under peak load. Forecast the seasonal peak, load-test its traffic mix and one-instance loss, and leave capacity headroom for that failure. Add the new schema compatibly, backfill and verify it, then canary new code while comparing order outcomes against the old version; remove the old structure only after every instance has moved. Maintain protected backups, rehearse a restore, and measure recovery time and surviving writes against scenario-specific RTO and RPO targets.

· · Finish

Review checklist

Without consulting notes, a reader should be able to define observability and operations from user outcomes; specify an SLI, SLO, and error budget and recompute the budget; choose metrics, logs, traces, and correlation fields for a distributed journey; estimate metric cardinality and plan sampling and retention; connect external checks and invariant alerts to an actionable runbook; stage a release and compatible schema change with outcome-based comparison; and plan capacity and verify recovery with load and restoration tests. A reader who can do all of these has covered the material.
