· · Start here

Learning objectives

  1. Distinguish robustness, fault tolerance, and high availability by the failure each addresses and the guarantee it preserves.
  2. Define availability, recovery time, and recovery point targets for a particular operation and failure scenario.
  3. Protect correctness when inputs are invalid, requests race, or an operation's outcome is unknown.
  4. Combine timeouts, bounded concurrency, circuit breaking, and load shedding to contain a slow dependency.
  5. Design retries so transient failures can recover without duplicating effects or overwhelming a service.
  6. Explain the detection, promotion, fencing, and routing steps of failover, including the data-loss trade-off in replication.
  7. Verify recovery and data safety with independent checks, fault injection, and backup restoration.

§1 · Definitions

Core concepts

This section defines a fault, a failure, robustness, fault tolerance, high availability, and availability. These terms separate the event that goes wrong from the behaviour the system promises when it does.

Definition

Fault A defect or adverse condition within or around a system, such as a crashed process, a slow network link, a malformed request, or a full disk.

Definition

Failure An observable departure from a system's required behaviour, such as returning a wrong answer, timing out, losing a confirmed write, or becoming unreachable.

Definition

Robustness The ability to handle invalid inputs, concurrency, resource limits, and unexpected conditions without violating the system's correctness rules.

Definition

Fault tolerance The ability to preserve a specified function or correctness guarantee despite faults in one or more components.

Definition

High availability A design goal of keeping specified functions accessible for a large fraction of requests or time, including during component failure and repair.

Definition

Availability The measured fraction of eligible requests that complete correctly within a stated time target, or the measured fraction of an agreed time window during which that condition holds; the measurement convention must be named.

A malformed order should be rejected without corrupting stored orders: that is robustness. A server may crash while another takes over and preserves acknowledged orders: that is fault tolerance. If customers can still place orders within the stated response target through most of the measurement window, the service meets a high availability goal. These properties overlap, but a service can be available while returning incorrect answers, or preserve every write while taking hours to recover.

A common confusion is to equate redundancy with all three properties. A second server can take traffic after a crash, but it cannot correct invalid state, detect every failure, or guarantee that a write reached the replacement. Each guarantee needs its own mechanism and measurement.

§2 · Reliability targets

Set reliability targets and failure boundaries

Definition

Service level objective (SLO) A numerical target for a service measure over a defined window, such as the share of checkout attempts completed correctly within a time limit over 30 days.

Definition

Recovery time objective (RTO) The longest acceptable time from a specified disruption until the affected function is restored.

Definition

Recovery point objective (RPO) The greatest acceptable age of the latest recoverable state at the moment of a specified disruption, which bounds potential data loss in time.

Definition

Failure domain A set of components that can be lost together because they share a cause, such as one host, availability zone, network, cloud account, or software release.

Definition

Availability zone A physically separate deployment area within a region, used as one possible boundary for infrastructure failures.

Definition

Single point of failure A component whose loss alone makes a required function unavailable because no other component can take over its role.

An availability target must name the operation, success condition, response limit, measurement window, and excluded or included traffic. A target for browsing can differ from one for committing an order. RTO and RPO must also name the scenario: loss of one process, a database primary, an availability zone, or an entire region can require different recovery mechanisms. A target is a design input; a drill supplies the measured result.

The diagram shows why two instances in one failure domain do not protect against every outage.

Read across the shared zone label: adding API instances protects against one process failing, but a zone loss still removes the whole path. Spreading the required components across independent domains changes which faults can be tolerated; a shared router or database can remain a single point of failure.

Worked examplean availability budget

Consider a 30-day measurement window and assume an operation has a time-based availability target of 99.9%. The window contains 30 × 24 × 60 = 43,200 minutes. The unavailable fraction is 1 − 0.999 = 0.001, so the budget is 43,200 × 0.001 = 43.2 minutes. Check: 43,200 − 43.2 = 43,156.8 available minutes, and 43,156.8 ÷ 43,200 = 0.999.

If the target is 99.99%, the unavailable fraction is 1 − 0.9999 = 0.0001, giving 43,200 × 0.0001 = 4.32 minutes. This arithmetic does not by itself define how partial failures count; the SLO must say whether a slow or incorrect request consumes the budget.

§3 · Correctness

Preserve correctness at request boundaries

Definition

Invariant A condition that must remain true across every permitted state transition, such as a confirmed order having one authoritative payment result.

Definition

Atomic operation A state change that either takes effect as one unit or does not take effect, so competing requests cannot observe a partial result.

Definition

Concurrency control A rule or mechanism that decides how overlapping operations on the same state interact, using transactions, conditional updates, locks, or version checks.

Robustness starts before a machine fails. Validate incoming data at the boundary, enforce business invariants at the authoritative state change, and reject impossible transitions. Input validation alone is insufficient: two valid requests can race and both try to reserve the final item. An atomic conditional update or transaction must make one succeed and the other receive a clear conflict. The database constraint remains useful even when application validation is present, because every write path must obey it.

The diagram traces two valid requests racing for one remaining unit.

The requests converge at one atomic decision. Checking stock in a separate read and then decrementing later would permit both requests to see the same unit; the protected transition makes the outcome depend on a single authoritative write.

An error response must also describe the state honestly. If a payment call times out after the remote side may have committed it, the result is unknown, not a confirmed failure. Recording that uncertainty and resolving it later is safer than declaring failure and starting an unrelated second charge. This leads to the retry rules below.

§4 · Failure containment

Contain slow dependencies and overload

Definition

Timeout A limit on how long a caller waits for an attempt or resource acquisition before it stops waiting.

Definition

Deadline The latest time by which the entire request must complete, passed through dependent calls as a remaining time budget.

Definition

Bulkhead An enforced cap on the threads, connections, in-flight calls, or other resources one class of work may hold.

Definition

Circuit breaker A control that stops most calls to a dependency after repeated failures or slow responses, then permits a limited number of probes to test recovery.

Definition

Load shedding Deliberately rejecting excess or lower-priority work when the service cannot complete it within its target.

Definition

Graceful degradation Serving a stated reduced function when an optional dependency is unavailable, while preserving required correctness and security controls.

Definition

Little's law For stable throughput, average work in progress equals the arrival rate multiplied by average time in the system: L = λW.

A slow dependency holds caller resources even when it has not returned an error. A timeout bounds each wait, and a propagated deadline stops later services from doing work after the original request can no longer use the result. A bulkhead limits how many callers can be trapped at once. A circuit breaker then reduces traffic to a dependency already known to be unhealthy. Load shedding limits total admitted work before queues and latency grow without bound. These controls cover different quantities, so one does not replace the others.

The diagram shows an optional recommendation service isolated from an order path.

The lower branch may fail or slow without taking every API worker. The fallback is valid because recommendations are optional. Authorisation, order totals, and payment status cannot be replaced by guesses merely to preserve a successful response.

Worked examplea slow dependency and a fixed pool

Consider an API offered 200 requests per second, each calling an optional dependency. Assume that dependency normally takes 50 ms = 0.05 s, and that the API has 200 request workers. For a stable system, Little's law gives required average in-flight calls as arrival rate times response time: 200/s × 0.05 s = 10 calls. If the dependency slows to an assumed 5 s while arrivals continue, sustaining that rate would require 200/s × 5 s = 1,000 concurrent calls. Check: 1,000 ÷ 10 = 100, matching the latency increase from 0.05 to 5 s.

The 200-worker pool cannot supply 1,000 concurrent calls, so throughput will fall and a queue will grow; the 1,000 figure is demand implied by the offered rate, not an observed steady state. A bulkhead of, say, an assumed 20 concurrent recommendation calls caps this optional branch at one tenth of the request-worker count, while a timeout releases permits and a fallback lets other requests proceed.

§5 · Safe retries

Retry safely after uncertain outcomes

Definition

Retry A new attempt at an operation after a previous attempt did not produce a usable result for the caller.

Definition

Idempotency A property of an operation for which repeating it has the same intended effect as one execution, within a stated scope and period.

Definition

Idempotency key A stable identifier supplied with repeated attempts so the receiver can return the first operation's recorded outcome instead of performing the effect again.

Definition

Exponential backoff with jitter A retry schedule whose delay grows between attempts and includes randomness, reducing synchronized retry waves.

Timeout does not prove that the remote operation failed. A request can commit just before the response is lost. Retry a write only when the operation is naturally idempotent or the receiver durably deduplicates attempts with the same idempotency key. The deduplication record and effect must be coordinated so two concurrent attempts cannot both pass a check. External effects, such as sending an email after a database commit, need their own duplicate protection.

Choose one layer to retry, distinguish transient failures from permanent rejections, cap attempts, and stop when the request deadline is exhausted. Backoff with jitter spreads retries in time; it does not create spare capacity. Under sustained overload, rejecting or deferring work is more useful than adding attempts.

The diagram traces the uncertain outcome of a write and its safe retry.

Read the second request as a query for the first attempt's outcome. It must not create another order. A new key would represent a new operation and could duplicate the effect.

Worked exampleretry amplification

Consider three sequential service layers, each configured for at most three attempts per call, including the first attempt. Assume every attempt fails in a way each layer considers retryable. The top layer makes 3 attempts to the middle layer; each middle attempt makes 3 attempts to the bottom layer's caller; each of those makes 3 attempts to the final dependency. The final dependency can receive 3 × 3 × 3 = 27 calls for one original request. Check by grouping: the first two layers produce 3 × 3 = 9 calls, and 9 × 3 = 27 at the bottom. Keeping retries at one chosen boundary caps this multiplication and makes the overall deadline easier to enforce.

§6 · Failover

Use redundancy and failover without losing data

Definition

Redundancy Extra components or copies arranged so a specified fault can occur without ending a required function.

Definition

Replication Copying state to another node so it can serve reads, preserve data, or assume responsibility after failure.

Definition

Failover Moving a workload or leadership role from a failed or unreachable component to a replacement.

Definition

Split brain A state in which two nodes simultaneously act as the sole owner of a role and can create conflicting histories.

Definition

Fencing A mechanism that prevents an old owner from changing protected state after a replacement has taken over, for example by rejecting writes with an obsolete generation number.

Stateless application instances can usually fail over by stopping traffic to an unhealthy instance and routing it to another with spare capacity. Stateful failover also needs a replacement with suitable data. The transfer has four steps: detect that the old owner cannot serve, choose a successor, prevent the old owner from writing, and redirect clients. A slow or partitioned old owner may still be alive, so detection alone cannot make two writers safe. Fencing must be enforced where the protected state is changed.

The diagram shows a leader replacement with a fenced old owner.

Follow the first line before failover and the last line after it. The generation change rejects writes from A even if it resumes; routing B without that guard would risk split brain. The router and the replacement's capacity also need independent failure protection.

Asynchronous replication acknowledges a write before its copy reaches the standby, so a promotion can lose recently acknowledged writes. Waiting for a durable copy before acknowledging reduces that risk but adds coordination latency and may block writes if the required copy is unavailable. Neither a replica nor automatic promotion protects against a mistaken delete or corrupting application write that is faithfully copied to every node.

Worked examplerecovery time and potential data loss

Consider a primary failure. Assume detection takes 8 seconds, successor selection and fencing take 7 seconds, and client redirection plus warm-up take 20 seconds. Recovery takes 8 + 7 + 20 = 35 seconds. Check: the three stages account for the whole interruption, so a 30-second RTO would be missed by 5 seconds under these assumptions.

Assume the primary accepted 1,000 writes per second and its standby was 0.2 seconds behind when the primary failed. If that lag consists of acknowledged writes that exist only on the failed primary, the potential loss is 1,000/s × 0.2 s = 200 writes. The multiplication checks the units, but actual loss depends on which writes reached durable storage and which replica is promoted; a measured replication position is needed to establish the real RPO.

§7 · Recovery

Restore, verify, and improve the recovery path

Definition

Backup A retained copy of data from which state can be restored after loss or corruption.

Definition

Point-in-time recovery Restoration to a selected moment by combining a base backup with a retained sequence of changes up to that moment.

Definition

Synthetic check A controlled request issued from outside the service to verify that a user-visible operation still works.

Definition

Fault injection A controlled test that removes or degrades a component to observe the system's actual failure and recovery behaviour.

Replication is for continued service after an infrastructure fault. A backup retained outside the affected failure domain is for recovering from deleted or corrupted data, including mistakes that replicas copy. A restoration test must prove that the data is readable, that the application can use it, and that the process completes within its RTO. For a time-based backup schedule, the interval since the last recoverable point informs the RPO; the duration of the restore informs the RTO.

The diagram places the two recovery objectives on opposite sides of a disruption.

Read leftward from failure to the last recoverable state for the data-loss window, and rightward to restored service for the interruption. A fast restart can have a poor RPO, while a slow restore can retain every write.

Monitor actual successful operations, error and latency rates, replication position, failover progress, queue age, and correctness invariants. An external synthetic check can detect outages that internal monitoring misses because it shares the failing system. Exercise process loss, slow dependencies, duplicate requests, primary promotion, and backup restoration, then compare measured recovery and data loss with their targets. Changes to software are another failure source: a staged rollout limits the fraction of traffic exposed to a bad release, but a restore still needs to account for incompatible data changes.

· · Review

Common mistakes

The first mistake is equating a fast response with a correct one. It happens because availability dashboards often count only HTTP status and latency. A successful response that lost an acknowledged write or bypassed an invariant is a failure under a correctness-aware SLO; define success to include the required outcome.

The second mistake is treating a second instance as complete failover. Both instances may share a database, router, region, or bad release, and a standby may lack capacity or current data. Map failure domains and test the whole path through detection, fencing, routing, and warm-up.

The third mistake is retrying every timeout. A timeout leaves the outcome uncertain, and retries at several layers multiply load. Use one bounded retry point, a shared deadline, and idempotency for effects that could otherwise be duplicated.

The fourth mistake is letting a slow optional dependency occupy all request workers. It happens because the dependency is still returning success, so error-based alarms and breakers may remain quiet. Apply a deadline and an independent concurrency cap, observe slow-call rate, and use a stated fallback for the optional function.

The fifth mistake is calling replicas a backup. Replicas reproduce deletes and corruption as well as valid writes. Retain protected backups or change logs in a separate failure domain and practise restoring them to a usable state.

· · Exercises

Practice questions

These questions mix recall, calculation and application across the whole guide, and each answer is collapsed beneath its question to be opened once the reader has worked out an answer.

Question 1 · distinction

An API rejects a malformed order without changing state, survives one API instance crashing, and serves checkout during that crash. Which observations demonstrate robustness, fault tolerance, and high availability?

Answer

Rejecting the malformed order without state change demonstrates robustness. Preserving the checkout function when an instance crashes demonstrates fault tolerance to that fault. Serving checkout during the crash contributes to high availability; whether the system meets a specific availability target still requires measurement over the stated window and latency limit.

Question 2 · calculation

An operation has a time-based 99.95% availability target over 30 days. How many minutes of unavailability does that permit?

Answer

The window is 30 × 24 × 60 = 43,200 minutes. The unavailable fraction is 1 − 0.9995 = 0.0005, so the budget is 43,200 × 0.0005 = 21.6 minutes. Check: 43,200 − 21.6 = 43,178.4 available minutes, and 43,178.4 ÷ 43,200 = 0.9995.

Question 3 · calculation

A primary accepts 2,000 writes per second, and a standby is 150 ms behind when the primary fails. Under the assumption that every write in that interval exists only on the primary, how many acknowledged writes could be lost by promoting the standby?

Answer

Convert 150 ms to 0.15 s. The potential loss is 2,000 writes/s × 0.15 s = 300 writes. The seconds cancel, leaving writes. This is an estimate under the stated assumption; inspect durable replication positions to determine actual loss.

Question 4 · application

A payment request times out after the provider may have committed a charge. What should the service record and how can it retry safely?

Answer

Record the attempt as having an unknown outcome rather than as a definite failure. Reuse the same provider idempotency key when retrying or query the provider for that attempt's result. Keep local state tied to one logical payment and reconcile it against the provider's authoritative result before confirming a new charge or reporting success.

Question 5 · open-ended

An online shop uses one database primary and two API instances in one zone. During a promotion, the old primary sometimes resumes, recommendations become slow, and a mistaken delete is copied to the standby. Propose changes that address correctness, availability, and recovery, and say how to test them.

Answer

Set separate success and recovery targets for browsing and checkout, including a rule for acknowledged orders. Place API capacity and a database standby across suitable independent failure domains, and verify that the router can move traffic with enough capacity left. Promote one primary at a time and enforce fencing at the write resource so the old primary cannot resume writes. Bound recommendation calls with timeouts, a bulkhead, and a breaker, and omit recommendations when the optional service fails; checkout correctness controls remain required. Keep protected backups and a change log for point-in-time recovery from the delete, because replication copies it. Test a slow recommendation dependency, an API loss, primary promotion while a request is in flight, attempted stale-primary writes, and a timed restore. Measure user-visible interruption and the set of acknowledged writes that survive each test.

· · Finish

Review checklist

Without consulting notes, a reader should be able to distinguish robustness, fault tolerance, and high availability; state a measurable success condition and calculate an availability budget; set RTO and RPO for a named failure; enforce invariants when requests race or outcomes are uncertain; bound waiting, concurrency, retries, and admitted load; explain each step of a fenced failover and its potential data-loss window; and prove recovery with independent checks and a tested restore. A reader who can do all of these has covered the material.
