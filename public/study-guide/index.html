Start here

Learning objectives

  1. Explain what a data model contains, distinguish the conceptual, logical and physical models, and say how much of the model to specify at the high-level and at the low-level design stage.
  2. Model a domain as entities, attributes and relationships, state the cardinality and participation of each relationship, resolve a many-to-many relationship into an associative entity, and distinguish an entity from a value object.
  3. Derive the access patterns of a system from its API surface and use them to justify every later storage decision.
  4. Choose primary and foreign keys and declare integrity constraints, distinguishing natural from surrogate keys.
  5. Identify functional dependencies, recognise the anomalies they cause, and decompose a table into third normal form or Boyce–Codd normal form.
  6. Calculate the depth of a B-tree index and the pages a query reads with and without it, order the columns of a composite index, and justify a denormalisation or read model with the mechanism that keeps it consistent.
  7. Choose a datastore family and a partition key from access patterns, calculate the load on the hottest shard, and plan a schema change with expand–migrate–contract.

§1 · Definitions

Core concepts

This section defines the central term, data model, and the terms every later section relies on: schema, entity, attribute, relationship, value object, and the three stages of data modelling. Each definition is set out in a callout where the term is first introduced, and the prose after it explains the mechanism.

Definition

Data model The description of what data a system holds, how the pieces relate to one another, which rules the data must obey, and which queries will be run against it, written independently of any particular set of stored values.

Definition

Schema The concrete statement of a data model in one database: its tables or collections, their fields and types, and the constraints on them.

Item 36 of the self-checklist defines the data model as "the entities, their relationships, and the queries I will run against them", and the inclusion of queries is deliberate: two models with identical entities can need different storage if they are read differently. The word schema comes from the Greek skhēma, shape or plan. The model is the design and the schema is that design expressed in the vocabulary a particular engine accepts. Values change constantly while the model changes rarely, which is why code is written against the model and keeps working as the data grows.

Definition

Entity A thing the system needs to remember and tell apart from other things of the same kind, such as a user, an order or a short link.

Definition

Attribute A single named property of an entity, such as a customer's email address, with a defined type and set of permitted values.

Definition

Relationship An association between entities that the system must record, such as "a customer places an order".

The source note traces the word entity to two traditions that are both still in use, and they explain why data design appears at both levels of design. The first is the entity–relationship model, which Peter Chen introduced in 1976 for designing databases: data is described as entities, their attributes and the relationships between them, and drawn as an entity–relationship diagram. In a relational schema an entity usually becomes a table, an attribute a column, and a relationship either a column that refers to another table or, for a many-to-many relationship, a table of its own.

Definition

Value object In domain-driven design, an object with no identity of its own, defined entirely by its attribute values, such as an amount of money or an address; two value objects with equal values are interchangeable.

The second tradition is domain-driven design, from Eric Evans's 2003 book of that name. There an entity is an object defined by a stable identity rather than by its values: an order stays the same order when its status changes from paid to shipped. A value object has no identity, so £40.00 is the same as any other £40.00, and changing it means replacing it. The distinction decides persistence as well as class design. An entity needs a key, because something must stay fixed while its attributes change; a value object is usually stored inline as columns of the entity that owns it, or embedded in its document, and needs no key of its own.

Definition

Conceptual model A model listing the entities and relationships and their business rules, in terms users recognise, with no reference to tables, keys or technology.

Definition

Logical model A model that adds attributes, keys and normalised dependencies in the terms of one family of data model, without choosing a product.

Definition

Physical model The model as implemented in one database product: tables, column types, indexes, partitioning, storage parameters and any deliberate denormalisation.

The three stages exist because the questions at each stage have different owners and change at different rates. Whether an order may exist without a customer is a business rule settled with domain experts. Whether the customer's details are stored once or repeated on each order is a structural decision settled by reasoning about dependencies. Whether the order table has an index on its date column is a performance decision settled by the queries. Keeping the stages apart means a change of database product touches only the physical model, and a change of indexing never alters what the data means.

The source note maps the conceptual and logical stages to high-level design (HLD), the view of a system as components and their connections, and the physical stage to low-level design (LLD), the view of what happens inside one component. It qualifies the mapping as rough, and the qualification matters: the same note places the choice of datastore family and partition key in HLD, and both are physical decisions. They are taken early because they shape the architecture diagram, whereas column types and indexes do not. The following diagram shows the three stages, the input that drives each one, and where the HLD and LLD boundary falls.

Read the diagram from left to right: each stage adds detail to the one before it, and the input underneath each stage is what justifies the detail it adds. The HLD bracket covers the first two stages plus the two physical decisions that shape the architecture; the LLD bracket covers the rest of the physical model. In a system design interview, step 5 of the script in the complete guide, "Data model and storage choice", gets 6 minutes, and the source note describes this as six minutes of a 45-minute round. The nine step durations in that script add up to 3 + 5 + 4 + 3 + 6 + 8 + 10 + 5 + 2 = 46 minutes, so the script overruns its own frame by one minute; the six minutes for data are unaffected.

The confusion learners most often have with the term data model is to treat it as a synonym for the list of tables. A list of tables is one physical rendering of a model, and it omits most of what the model contains: the business rules that make relationships mandatory or optional, the dependencies that justify how attributes were grouped, the access patterns that justify the indexes and the datastore, and the reasons for any departure from the logical design. Two databases with identical tables can encode different models, for example if one requires every order to have a customer and the other allows orphaned orders.

§2 · Conceptual model

Entities, relationships and cardinality

The source notes list entities and say that "a user owns many short URLs", but they do not explain how to state a relationship precisely, so this section goes beyond the notes. It uses a running example for the rest of the guide, the online shop from the storage note's curriculum: customers place orders, each order contains one or more lines, and each line refers to a product. The example is illustrative.

The method is to read the requirements for nouns the business needs to keep facts about, which become candidate entities, and for verbs connecting them, which become candidate relationships. A noun that only describes another, such as "email address" in "each customer has an email address", is an attribute. The test for promoting an attribute to an entity is whether the system must record facts about it in turn: a delivery address printed once on a label can be a value object stored on the order, but an address that customers save, name and reuse across orders has facts and an identity of its own, and becomes an entity.

Definition

Cardinality The maximum number of instances of one entity that can be associated with a single instance of another through a relationship, stated as one or many.

Definition

Participation Whether every instance of an entity must take part in a relationship (mandatory) or may exist without taking part (optional); also called optionality or minimum cardinality.

Cardinality is borrowed from set theory, where it means the number of members of a set. In modelling it answers "at most how many?", and participation answers "at least how many?", so together they give each end of a relationship a range such as 0..* or 1..1. A customer places zero or more orders, because a newly registered customer has none, while an order is placed by exactly one customer, because an order without a customer has no one to bill. Both ends matter because they turn into different physical constructs: the "exactly one" end becomes a foreign key column that may not be null, and the "zero or more" end needs no column at all.

The relationship between orders and products is many-to-many: one order holds several products and one product appears in many orders. A relational table cannot represent this with one column, because a column holds one value per row, and storing a list of product identifiers in one field breaks first normal form, defined in "Functional dependencies and normalisation".

Definition

Associative entity An entity introduced to resolve a many-to-many relationship, with one instance per pairing of the two related entities and any facts that belong to the pairing; also called a junction, link or bridge table.

In the shop the associative entity is the order line. It replaces one many-to-many relationship with two one-to-many relationships, and it gives a home to facts that belong to neither side alone: the quantity ordered and the price charged on that order for that product. The price charged is a property of the sale, not of the product, which is why the order line is an entity and not merely a pair of pointers. The following diagram shows the shop's conceptual model, with each relationship labelled by its verb and each end by its range.

Read each range as belonging to the entity it sits next to: the 0..* beside Order says a customer places zero or more orders, and the 1..1 beside Customer says each order has exactly one customer. The 1..* beside Order line says an order has at least one line, a rule that a foreign key cannot enforce on its own, because it constrains the parent rather than the child; it is usually checked by the application, or by inserting the order and its lines in one transaction.

§3 · Checklist item 36

Access patterns and the order of design

Definition

Access pattern A specific read or write the system performs, stated with its input, its result and how often it happens, such as "fetch an order with its lines by order identifier, about 500 times per second".

The conceptual model in "Entities, relationships and cardinality" says what exists; access patterns say how it is used, and the source notes treat them as the decisive input. The storage note puts the principle as "You don't choose a database type. You choose an access pattern, and the type follows", and the entity note says access patterns matter most at the HLD stage because they decide the storage choice and the partitioning. An access pattern is more than a query: its frequency and latency target decide whether it needs an index, a copy, or a different store.

The dependency between the API and the data model can be resolved in four steps. A short list of entity names comes first, because API resources are those entities. The API surface comes second, because each endpoint is a read or write the storage layer must serve. The data model and storage choice come third, derived from the access patterns those endpoints imply, and the architecture comes fourth. Designing the schema first means choosing storage before knowing which queries it must serve, which the note says leads to tables no endpoint reads and to a datastore chosen by habit.

The following table lists the shop's main access patterns, and it is useful because every later decision in the guide refers back to one of its rows. The frequencies are assumptions for the example, not figures from the notes.

The third row, an atomic write across three entities, is the one that points to a relational store in "Choosing a datastore family", and the second row is the one that motivates the composite index in "Indexes". The process is not strictly linear: modelling the data often exposes a query no endpoint asked for, and the notes' response is to add the endpoint rather than treat the API as finished.

§4 · Logical model

Keys and integrity constraints

The entity note lists "primary keys and foreign keys" and "nullability and uniqueness constraints" among the LLD decisions without explaining how to choose them, so this section goes beyond the notes. Translating the conceptual model into a logical relational model needs a way to identify each row and a way for one table to refer to another, and keys provide both.

Definition

Candidate key A set of attributes whose values are unique for every row and from which no attribute can be removed without losing that uniqueness.

Definition

Primary key The candidate key chosen to identify rows in a table and to be referenced by other tables.

A customer table might have a customer number and an email address that are each unique, so both are candidate keys. Minimality is what separates a candidate key from its supersets: the pair (customer number, email) is also unique but is not a candidate key, because the customer number alone suffices. Choosing which candidate becomes the primary key is a design decision, and the main criterion is stability, because every foreign key referring to the primary key must change whenever its value does. This is the persistence form of the entity–value object distinction in "Core concepts": the primary key is the identity that stays fixed while everything else about the entity changes.

Definition

Natural key A key made of attributes with meaning in the domain that exist independently of the database, such as an ISBN, a SKU or an email address.

Definition

Surrogate key A key with no domain meaning, generated by the system solely to identify rows, such as an identity integer or a UUID.

The trade-off is between meaning and stability. A natural key needs no extra column and is readable, but it inherits every change the outside world makes to it: customers change email addresses and suppliers reissue product codes. A surrogate key never needs to change, because nothing outside depends on its value, but it does not prevent duplicates, since the same customer registered twice receives two surrogate values. The common practice is a surrogate primary key plus a unique constraint on the natural candidate key, which keeps references stable and still rejects duplicates. The URL shortener in the entity note is a case where the natural key is the right primary key: short_code is generated by the system, never changes, and is the value every lookup supplies.

Definition

Foreign key A column or set of columns whose values must match a candidate key, normally the primary key, of a row in a referenced table.

Definition

Integrity constraint A rule declared in the schema that the database checks on every change, rejecting any change that violates it: NOT NULL, UNIQUE, CHECK, primary key and foreign key constraints.

Definition

Referential integrity The property that every foreign key value refers to a row that exists, so no reference is left dangling.

Foreign keys turn relationships into structure. "A customer places orders" becomes a customer_id column on the order table, on the "many" side, and the participation rule "every order has exactly one customer" becomes NOT NULL. When a referenced row is deleted the schema declares what happens: RESTRICT refuses the deletion, CASCADE deletes the referring rows too, and SET NULL clears the reference. The choice follows from the domain: cascading the deletion of a customer into their orders would destroy financial records. The storage note calls this "constraints as truth": correctness enforced by the engine rather than by every application that touches the table. The illustrative schema that follows applies these rules to the shop.

The composite primary key on order_line states a business rule as well as an identity: a product appears at most once per order, so a second unit raises the quantity. If the business wanted two lines for the same product at different discounts, the key would become a line number within the order, which shows that key choice is a statement about the domain.

Keys and constraints also depend on the datastore, and here the entity note mixes two families. Its HLD example puts ShortUrl in a key-value store partitioned on short_code, but its LLD example writes owner_id BIGINT REFERENCES users(id) and an index on owner_id, which are relational constructs. A key-value store enforces no foreign keys, and it serves "list my links" only through a secondary index it maintains, such as a DynamoDB global secondary index, or one the application maintains; the storage note warns that owning such an index means owning its consistency. The LLD schema as written is correct for a relational store, which is a defensible choice for a URL shortener at moderate scale, but it then contradicts the HLD choice. Either the HLD should say relational, or the LLD should replace the foreign key with an application-level check and name the secondary index.

§5 · Logical model

Functional dependencies and normalisation

The entity note defines normalisation in one clause, "how far data is split into separate tables so that each fact is stored once", and this section supplies the theory behind it, going beyond the notes. Keys say which attributes identify a row; normalisation uses the same idea to decide which attributes belong together, so that no fact is stored in many rows where the copies could disagree.

Definition

Functional dependency A constraint written X → Y, meaning any two rows that agree on attributes X must also agree on attributes Y; X is the determinant.

A functional dependency is a statement about the domain, not about the rows present: customer_id → customer_email holds because the business assigns one email per customer, and it would hold in an empty table. A candidate key is exactly a minimal set of attributes that determines every other attribute. Normalisation finds dependencies whose determinant is not a key and moves them into tables where it is.

Definition

Data anomaly An inconsistency or loss of information caused by redundant storage: an update anomaly (a change must be repeated in many rows and some are missed), an insertion anomaly (a fact cannot be recorded without an unrelated fact), or a deletion anomaly (removing one fact removes another).

Definition

Normal form A condition on a table's structure that rules out one class of anomaly; the forms are numbered in increasing strictness, each including the one before.

E. F. Codd, who proposed the relational model at IBM in 1970, defined the first three normal forms in 1970 and 1971, borrowing the term from mathematics, where a normal form is a standard representation of an object. Each form forbids one shape of dependency, so they can be learned as a sequence of questions asked of a table.

Definition

First normal form (1NF) Every attribute holds a single, indivisible value per row, with no lists or repeating groups in one field.

Definition

Partial dependency A dependency in which a non-key attribute depends on only part of a composite candidate key.

Definition

Second normal form (2NF) First normal form, and no non-key attribute has a partial dependency on a candidate key.

Definition

Transitive dependency A dependency A → C that holds only because A → B and B → C, where B is not a candidate key.

Definition

Third normal form (3NF) Second normal form, and no non-key attribute is transitively dependent on a candidate key: every non-key attribute depends on the key, the whole key, and nothing but the key.

The mechanism behind each form is the same. A partial or transitive dependency means some attribute is determined by something smaller than the row's key, so the same determinant value, and with it the same dependent value, recurs in every row that shares it. Moving the dependency into its own table, keyed by its determinant, stores the dependent value once per determinant value instead of once per row.

Definition

Lossless-join decomposition A split of one table into several such that joining the parts on their shared attributes reproduces exactly the original rows, none lost and none invented.

For a split into two tables, the decomposition is lossless when the shared attributes form a key of at least one part, which is why each normalisation step keeps the determinant in both tables: as the primary key of the new table and as a foreign key in the old one.

Worked examplenormalising the shop's order data

Suppose a prototype stores everything in one table, sales(order_id, placed_at, customer_id, customer_name, customer_email, product_id, product_name, list_price, quantity, unit_price), one row per product per order, with primary key (order_id, product_id). Every field holds one value, so it is in 1NF.

Step 1 writes the dependencies from the business rules: order_id → placed_at, customer_id; customer_id → customer_name, customer_email; product_id → product_name, list_price; and (order_id, product_id) → quantity, unit_price.

Step 2 checks 2NF. placed_at and customer_id depend on order_id alone, and product_name and list_price on product_id alone; all four are partial dependencies. Splitting them out gives order(order_id, placed_at, customer_id, customer_name, customer_email), product(product_id, product_name, list_price) and order_line(order_id, product_id, quantity, unit_price).

Step 3 checks 3NF. In order, order_id → customer_id → customer_name, customer_email, and customer_id is not a key of order, so the name and email are transitively dependent. Splitting gives customer(customer_id, customer_name, customer_email) and order(order_id, placed_at, customer_id), which is the schema in "Keys and integrity constraints".

Step 4 measures the redundancy removed. Assume 200 customers, 1,000 orders of 3 lines each, and 30-byte emails; these are assumptions for the example. The single table has 1,000 × 3 = 3,000 rows, so each email is stored 3,000 ÷ 200 = 15 times on average, occupying 3,000 × 30 = 90,000 bytes, against 200 × 30 = 6,000 bytes in customer. As a check, 90,000 ÷ 6,000 = 15, the average number of copies. Storage is the smaller benefit: in the single table a change of email must update 15 rows, and any row missed leaves the customer with two emails. The table also has an insertion anomaly, because a new product cannot be recorded until someone orders it, and a deletion anomaly, because deleting the only order for a product deletes its name and price.

Read each branch as one dependency leaving the parent table together with its determinant, which stays behind as a foreign key so the split remains lossless. The leaves are the four tables of the final schema.

Definition

Boyce–Codd normal form (BCNF) For every non-trivial dependency X → Y in the table, X is a superkey, meaning X contains a candidate key.

Raymond Boyce and Codd defined BCNF in 1974 to close a gap in 3NF, which constrains only dependencies of non-key attributes. The gap appears with overlapping composite candidate keys. In a tutoring service where each tutor teaches one course and each student has one tutor per course, tutoring(student, course, tutor) has (student, course) → tutor and tutor → course, so both (student, course) and (student, tutor) are candidate keys. Every attribute belongs to a candidate key, so the table is in 3NF, yet tutor → course repeats each tutor's course for every student. Splitting into tutor_course(tutor, course) and tutor_student(student, tutor) reaches BCNF, at the cost that "one tutor per student per course" can no longer be enforced by a key on one table. The shop has no overlapping keys, so there 3NF and BCNF coincide.

§6 · Checklist item 38

Indexes

The normalised model in "Functional dependencies and normalisation" says what is stored; the physical model decides how, so that the access patterns from "Access patterns and the order of design" run fast enough. Item 38 of the checklist asks which indexes the queries need and what each costs. Databases store tables in fixed-size pages, typically 4 to 16 KB, and read whole pages at a time, so the cost of a query is approximately the number of pages it touches.

Definition

Index An auxiliary structure that maps column values to row locations, so that queries find rows without scanning the whole table.

Definition

B-tree A balanced, sorted tree of fixed-size pages, each holding many keys and child pointers, with every leaf at the same depth; the default index structure in relational databases.

Definition

Fanout The number of child pointers a B-tree page holds, roughly the page size divided by the size of one key-and-pointer entry.

Rudolf Bayer and Edward McCreight described the B-tree at Boeing in 1970; the meaning of the B was never officially stated. The structure works because its fanout is large: each level multiplies the reachable rows by hundreds, so depth grows with the logarithm of the row count to the base of the fanout. A lookup reads one page per level from root to leaf, then the table page the leaf points to.

Worked examplechecking the glossary's "a few pages"

The index glossary entry says a composite index on (customer_id, created_at) turns "latest 20 orders for a customer" from a scan of 50 million rows into "a read of a few pages". Assume 8,192-byte pages, 16-byte index entries and 200-byte rows, and ignore page headers; these are assumptions, not figures from the note.

The fanout is 8,192 ÷ 16 = 512. Two levels reach 512 × 512 = 262,144 rows, fewer than 50,000,000; three reach 262,144 × 512 = 134,217,728, more, so the index is 3 levels deep (check: log 50,000,000 ÷ log 512 = 7.699 ÷ 2.709 = 2.84, rounded up to 3). The descent reads 3 pages, and the 20 adjacent entries for one customer fit in one leaf, since 20 × 16 = 320 bytes. Fetching the 20 rows can then cost up to 20 table pages, because a customer's orders are scattered across the table in the order they were placed. The indexed query reads up to 3 + 20 = 23 pages.

Without the index, each page holds 8,192 ÷ 200 = 40.96, so 40 whole rows, and the scan reads 50,000,000 ÷ 40 = 1,250,000 pages, about 1,250,000 ÷ 23 = 54,348 times as many. The glossary's claim holds for the index itself, but "a few pages" understates the query by the row fetches, which dominate. A covering index, defined next, removes them and brings the query down to the 3 pages of the descent, or 4 if the customer's entries straddle two leaves.

Definition

Covering index An index that contains every column a query needs, so the query is answered from the index alone without reading the table.

Definition

Composite index An index on several columns in a fixed order, sorted by the first, then the second within equal values of the first, so it serves conditions on any leading prefix of its columns.

Definition

Selectivity The fraction of a table's rows a condition matches; an index helps only when the condition is selective enough that following pointers costs less than scanning.

Column order in a composite index comes from the query: equality conditions first, then the column used for a range or sort. (customer_id, placed_at) serves "this customer's orders, newest first", because one customer's entries are contiguous and already sorted by time, but it cannot serve a query on placed_at alone, because rows from one day are scattered across every customer's range. The glossary names the two classic failures: ordering the columns wrongly, and wrapping the indexed column in a function, as in WHERE date(placed_at) = …, which hides the stored values from the planner. Selectivity sets the limit from the other side: a condition matching 30% of the 50 million rows needs up to 15,000,000 random page reads through the index, twelve times the 1,250,000 sequential reads of a scan, so the planner ignores the index.

Indexes are paid for on every write. Each insert, delete, and update of an indexed column must change every index, so a table with four secondary indexes turns one row insert into one table-page write and four index-leaf writes, five instead of one, before page splits. The rule that follows is to index for the access patterns the system has, not for every column a query might mention. The illustrative statements below index the shop's two non-key patterns.

§7 · Physical model

Denormalisation and read models

Definition

Denormalisation The deliberate storage of redundant, pre-joined or derived copies of data in a normalised schema, to serve particular reads cheaply, with the copies kept consistent by a stated mechanism.

Indexes make it cheaper to find rows; denormalisation makes it cheaper to assemble them, by storing the result of a join or computation in advance. The entity note places it among the LLD decisions: where data is "deliberately duplicated for read speed". It differs from an unnormalised design in that it is a decision taken after normalising, for a named read, with a named mechanism for consistency. It reintroduces exactly the update anomaly that "Functional dependencies and normalisation" removed, so it pays only where the read is far more frequent than the write it complicates.

Worked examplea stored order total

The order history page shows each order's total, which otherwise means reading and summing every line. An order has three lines: 2 units at £12.50, 1 at £40.00 and 3 at £4.00. The line amounts are 2 × 12.50 = £25.00, 1 × 40.00 = £40.00 and 3 × 4.00 = £12.00, and the total is 25.00 + 40.00 + 12.00 = £77.00. Adding order_total to customer_order lets the page read one row per order instead of one per line. The column is a second copy of a fact the lines determine, so the lines and the total are written in one transaction, or a trigger recomputes the total when a line changes, and a reconciliation query that recomputes totals from lines checks that the mechanism works. Orders rarely change once placed, so the write cost is small and the saving applies to every page view.

Definition

CQRS Command Query Responsibility Segregation: maintaining separate read models, shaped to particular screens, that are updated from the changes made to the write model.

CQRS generalises denormalisation from one column to whole read models. The glossary's example is an order-history page that reads a customer_order_summary document built from order, payment and shipment events, instead of joining four tables per request. Because the read model is updated after the write commits, typically from an event stream or change data capture, it lags its source, and the contract of the screen must tolerate that lag. The glossary's failure mode is the general risk of every denormalisation: updating the copy from some write paths but not others, so the copies drift permanently. Routing all updates through one propagation path, rather than through each piece of code that writes, is what prevents it.

§8 · Checklist item 37

Choosing a datastore family

The sections up to "Denormalisation and read models" assume a relational store. To decide which storage technology fits the queries, answer five questions before naming a product: what the queries are, the read and write shape, the consistency each operation needs, the access keys, and the operational reality.

Definition

Datastore family A class of databases sharing one data model and its trade-offs: relational, document, key-value, wide-column or graph.

Definition

Partition key The attribute whose value decides which partition, and so which machine, holds a record; queries that supply it touch one partition.

The storage note singles out the access key: whether there is "a single natural partition key that almost every query includes" decides between relational and the other families more often than anything else. When every query supplies the key, data can be spread across machines by that key and each query sent to one machine. When queries filter on different attributes, or join entities, a store that only finds data by key cannot answer them without copies. Two points from the note qualify the comparison. A document store is not schemaless: the schema moves from the database into every application version that ever wrote data, which the note calls schema-on-read, and Postgres JSONB offers most of the document benefits with transactions and constraints. And every additional engine costs, in the note's words, "a backup, a migration path and a page at 3 a.m.", which the families glossary entry restates as counting each additional store as an operational cost.

§9 · Checklist items 40 and 41

Partitioning and hot keys

The partition key from "Choosing a datastore family" also decides how data is spread across machines once one machine is not enough. The entity note includes the partition key in HLD for this reason: it determines which queries stay on one machine, and so shapes the architecture.

Definition

Sharding Horizontal partitioning: splitting a dataset across nodes by a partition key, using hash or range assignment, so that write capacity and storage grow with the number of shards.

Definition

Hot key A partition key that receives a disproportionate share of traffic, saturating the shard, cache node or pipeline that owns it.

Hash assignment spreads keys evenly by count; range assignment keeps neighbouring keys together so range queries touch few shards, at the risk that new keys, such as today's timestamps, all land on one shard. The sharding glossary's example partitions orders by a hash of customer_id across 16 shards, so each customer's orders sit on one shard and a per-customer query touches one node, while a query by product touches all 16. The partition key thus fixes both the balance of load and the cost of every query that does not include it. Item 40 adds that the key should spread traffic as well as data, and the hot key glossary names the failure: checking balance by key count rather than traffic.

Worked examplethe hottest shard

The sharding glossary describes a tenant that generates 40% of requests. With 16 shards partitioned by a hash of tenant, an even spread would give each shard 100 ÷ 16 = 6.25% of traffic. The hot tenant's 40% lands on one shard, and the other 60% spreads over all 16, adding 60 ÷ 16 = 3.75% to each. The hot shard carries 40 + 3.75 = 43.75%, which is 43.75 ÷ 6.25 = 7 times the average, while the other 15 carry 3.75% each. As a check, 43.75 + 15 × 3.75 = 43.75 + 56.25 = 100%.

Definition

Key salting Appending a suffix to a hot key so that its records spread across several partitions.

Salting the tenant's key with 8 suffixes, assuming they hash to 8 different shards, spreads its 40% as 40 ÷ 8 = 5% per shard. Those 8 shards carry 5 + 3.75 = 8.75% each, 8.75 ÷ 6.25 = 1.4 times the average, and the other 8 carry 3.75% (check: 8 × 8.75 + 8 × 3.75 = 70 + 30 = 100%). The cost is that every read of that tenant's data must now query 8 partitions and merge the results, which is why salting is applied only to keys known to be hot. Wide-column stores face the related problem of unbounded partitions, which the storage note handles by bucketing, partitioning a chat channel's messages by channel and month so that no partition grows without limit.

§10 · Checklist item 39

Schema evolution

Every decision so far is made against today's requirements, and item 39 asks how the schema will change without breaking running code. The difficulty comes from deployment: in a system serving traffic, the database changes at one moment but application servers are replaced one by one, so old and new code run against the same schema at the same time. A change that removes something the old code reads causes errors for as long as any old server runs, and a change that destroys data cannot be undone by reverting code.

Definition

Migration A versioned, repeatable script that changes a schema, and if necessary its data, from one version to the next, stored with the application code and applied in order to every environment.

Definition

Backward compatibility The property of a schema change that code written for the previous version keeps working against the new one.

Definition

Expand–migrate–contract Making a breaking change as backward-compatible steps: add the new structure alongside the old, dual-write and backfill, switch reads, then remove the old structure; also called parallel change.

The zero-downtime migration glossary uses renaming user.name to full_name as its example, and the following diagram shows its steps as states, each deployed and verified before the next.

Read it from top to bottom as a sequence in which every state is safe for both the code version before it and the one after it. While both columns are written, the system can return to reading name at any point. The glossary's failure mode is collapsing the last two states: dropping the column in the same release that stops writing it breaks instances of the previous version still running during a rolling deploy. The illustrative migrations that follow implement the steps.

The price is time and temporary complexity: the change spans several releases and doubles the write paths while it runs, as the glossary notes. The same pattern handles changes of cardinality, such as letting a customer hold several emails, where the expand step creates a customer_email table rather than a column, and it handles moving data between datastores, where the dual write goes to two engines.

Review

Common mistakes

The first mistake is choosing a datastore before listing the access patterns. It happens because a familiar product, or one described as scalable, feels like a safe starting point, and the costs appear only when a query arrives that the store cannot serve. The families glossary names the result: a document or wide-column store chosen "for scale", followed by a need for joins and multi-row transactions it does not provide. What is correct is the order in "Access patterns and the order of design": entity names, then endpoints, then access patterns, and only then the family, defaulting to relational until a named constraint forces otherwise.

The second mistake is using a changeable natural key, such as an email address, as the primary key. It happens because the value is already unique and saves a column. When it changes, every foreign key referring to it must change in the same transaction, and external systems holding the old value point at nothing. What is correct is a surrogate primary key with the natural key declared unique, as set out in "Keys and integrity constraints", unless the natural key is system-generated and immutable, like a short code.

The third mistake is storing the current value where the historical value is the fact, for example reading an order line's price from the product table. It happens because "price" looks like one attribute when the domain has two: the product's current list price and the price charged on a past sale. Joining to the product makes every past invoice change when the price list changes. What is correct is the dependency analysis in "Functional dependencies and normalisation", which puts unit_price on the order line; this is not denormalisation, because the two prices are different facts.

The fourth mistake is checking partition balance by key count rather than traffic. It happens because hash partitioning makes key counts even by construction, and the dashboard shows equal shard sizes. One key carrying a large share of requests still saturates its shard, as the worked example in "Partitioning and hot keys" shows with one shard at 7 times the average. What is correct is to measure traffic per key, choose a partition key whose traffic spreads, and salt or isolate the keys known to be hot.

The fifth mistake is dropping an old column in the same release that stops writing it, or updating a denormalised copy from only some write paths. Both happen because the change looks complete from the point of view of the newest code. Instances of the previous version are still running during a rolling deploy, and write paths that were missed keep producing stale copies. What is correct is to keep the irreversible contract step for a later release, as in "Schema evolution", and to propagate every denormalised copy through one path, as in "Denormalisation and read models".

Exercises

Practice questions

The questions that follow mix recall, calculation and application across the whole guide. Each answer is collapsed beneath its question; open it once you have worked out your own answer.

Question 1 · recall

For each decision about the shop, state whether it belongs to the conceptual, logical or physical model, and whether it is taken at the HLD or the LLD stage.

  1. Every order is placed by exactly one customer.

    Answer

    Conceptual, and HLD: it is a business rule a domain expert can confirm without knowing anything about databases.

  2. Orders are stored in Postgres and partitioned by a hash of customer_id.

    Answer

    Physical, but taken at HLD: the datastore family and partition key shape the architecture, which is why the entity note places them in HLD although they are physical decisions.

  3. The order table has a covering index on (customer_id, placed_at).

    Answer

    Physical, and LLD: it changes how fast a query runs, not what the data means, and it does not change the architecture.

Question 2 · distinction

Distinguish an entity from a value object, and say how each is usually persisted.

Answer

An entity has a stable identity that persists while its attributes change, as an order stays the same order when its status changes; a value object has no identity and is defined by its values, as £40.00 equals any other £40.00. An entity therefore needs a primary key. A value object is usually stored inline, as columns of the entity that owns it or embedded in its document, and is replaced rather than updated.

Question 3 · calculation

A table holds 2,000,000,000 rows. Its B-tree index uses 8,192-byte pages and 20-byte entries. How many levels does the index have, and how many page reads does a single-row lookup need, counting the table page?

Answer

The fanout is 8,192 ÷ 20 = 409.6, so 409 whole entries. Three levels reach 409 × 409 × 409 = 167,281 × 409 = 68,417,929 rows, fewer than 2,000,000,000; four reach 68,417,929 × 409 = 27,982,932,961, more, so the index has 4 levels. As a check, log 2,000,000,000 ÷ log 409 = 9.301 ÷ 2.612 = 3.56, rounded up to 4. A lookup reads 4 index pages and 1 table page, 5 in total.

Question 4 · calculation

A dataset is hash-partitioned across 32 shards, and one key carries 25% of all traffic. What share does the hottest shard carry, relative to the average? What does salting the key with 16 suffixes, landing on 16 different shards, reduce that to?

Answer

The average shard carries 100 ÷ 32 = 3.125%. The other 75% spreads as 75 ÷ 32 = 2.34375% per shard, so the hot shard carries 25 + 2.34375 = 27.34375%, which is 27.34375 ÷ 3.125 = 8.75 times the average. With 16 salts the key adds 25 ÷ 16 = 1.5625% to each of 16 shards, which then carry 1.5625 + 2.34375 = 3.90625%, or 3.90625 ÷ 3.125 = 1.25 times the average. Check: 16 × 3.90625 + 16 × 2.34375 = 62.5 + 37.5 = 100%. Reads of that key now query 16 partitions.

Question 5 · application

A university records enrolment(student_id, student_name, module_code, module_title, lecturer_id, lecturer_name, grade), one row per student per module, and each module has exactly one lecturer. State the dependencies and key, the normal form violated, and a 3NF decomposition.

Answer

The dependencies are student_id → student_name, module_code → module_title, lecturer_id, lecturer_id → lecturer_name and (student_id, module_code) → grade, so the key is (student_id, module_code).

  • The table violates 2NF, because student_name depends only on student_id, and module_title and lecturer_id only on module_code.
  • After removing those, a module table holding lecturer_name would violate 3NF through module_code → lecturer_id → lecturer_name.
  • The 3NF schema is student(student_id, student_name), module(module_code, module_title, lecturer_id), lecturer(lecturer_id, lecturer_name) and enrolment(student_id, module_code, grade); each determinant stays behind as a foreign key, so the decomposition is lossless.

Question 6 · misconception

A colleague proposes a document store "because it is schemaless, so we will never need migrations". What is wrong with the reasoning?

Answer

A document store does not remove the schema; it moves it from the database into every application version that wrote data, which the storage note calls schema-on-read. Old documents keep their old shape, so the code must either handle every shape ever written or the documents must be migrated, and without engine-side constraints nothing reports how many shapes exist. Changing a field still needs expand–migrate–contract, with the backfill rewriting documents instead of rows. If flexible fields are the real need, Postgres JSONB provides them with transactions and constraints.

Question 7 · open-ended, combining subtopics

The shop now sells clothing in sizes and colours, takes payment in euros as well as pounds, and expects one wholesale customer to place 30% of all orders. Describe the changes to the data model, covering entities and relationships, keys, normalisation, indexes, partitioning, and how you would deploy the change.

Answer

A complete answer combines the subtopics as follows.

  • Entities: add product_variant in a one-to-many relationship with product, because size and colour describe the item sold and stock is held per variant; give it a surrogate key and unique constraints on its SKU and on (product_id, size, colour), and make order_line refer to the variant.
  • Normalisation: price now depends on the pair (variant, currency), so add variant_price(variant_id, currency, amount) rather than two price columns; add currency to the order and keep unit_price on the line as the amount charged, a historical fact. Money is a value object, an amount with its currency, stored inline.
  • Indexes: add product_variant(product_id) for the product page, which lists all variants of one product.
  • Partitioning: if orders are sharded by customer_id, the wholesale customer makes one shard hot; salt that customer's key, or give it a dedicated partition, and measure traffic per key rather than key counts.
  • Deployment: use expand–migrate–contract, creating the new tables, backfilling one default variant and one GBP price per product, dual-writing, switching reads, and dropping product.list_price and the old line reference in a later release.
