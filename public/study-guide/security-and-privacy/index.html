· · Start here

Learning objectives

  1. Explain how security and privacy requirements differ and where they affect a system design.
  2. Map sensitive assets, data flows, trust boundaries, and likely threats before choosing controls.
  3. Distinguish authentication from authorization and design access checks for users, services, and individual resources.
  4. Protect personal and confidential data across collection, processing, storage, sharing, backup, and deletion.
  5. Choose defenses against malformed input, injection, automated abuse, and overloaded shared resources.
  6. Design audit records and incident signals that support investigation without exposing secrets or unnecessary personal data.
  7. Trace each important risk to a design control and a test that can show whether the control works.

§1 · Definitions

Core concepts

This section defines security, privacy, and the boundaries that make their requirements concrete in a distributed system.

Definition

Security The protection of a system and its data against unauthorized access, change, or disruption.

Definition

Privacy The appropriate handling of information about people across its full life cycle, including what is collected, why it is used, who receives it, and when it is removed.

Definition

Asset Something whose loss, disclosure, alteration, or unavailability would cause harm, such as an account, payment record, signing key, or service capability.

Definition

Trust boundary A point where data or a request moves between parties or components with different authority or security assumptions.

Definition

Threat model A structured account of assets, data flows, trust boundaries, possible misuse, and the controls chosen to reduce risk.

Security asks whether an actor can do something harmful; privacy also asks whether a permitted use of personal data is appropriate and limited. Encryption can protect a database from disclosure, but it does not justify collecting an unnecessary field or keeping it indefinitely. Conversely, collecting little data reduces exposure but does not stop someone with a stolen session from reading what remains. Both concerns must be expressed as requirements for named journeys, stores, and operators.

The common confusion is to treat security and privacy as a checklist appended after the architecture. Component boundaries, identity propagation, data copies, and retention choices determine what can be protected later. A design review therefore starts with the assets and flows, then tests each proposed control against a specific risk.

§2 · Threat modeling

Map assets, flows, and trust boundaries

Definition

Attack surface The set of interfaces and paths through which an actor can interact with or influence a system.

Definition

Threat A plausible way an asset could be disclosed, altered, misused, or made unavailable.

Start with a user journey and draw the data it moves. A customer viewing an order may cross a browser-to-edge boundary, an edge-to-service boundary, and a service-to-database boundary. A background worker and a support console create additional paths to the same record. Mark where identity is established, where authorization is checked, where sensitive fields are copied, and which outside services receive them. The diagram should include logs, queues, backups, exports, and administrative tools when they carry the same data.

The diagram shows a simplified order-read path and its secondary copies.

Read each arrow as a point where a request or data copy needs an explicit owner and policy. The browser is outside the service's trust boundary; a support console is another entry point, not automatically a trusted exception. OWASP's Threat Modeling Cheat Sheet uses data flows and trust boundaries to find risks that a component diagram alone can miss.

For each asset, ask how a caller could impersonate an owner, change a record, read another customer's record, exhaust a shared resource, or bypass a workflow. Rank risks by likely impact and exposure, then record the control and evidence needed for each. A threat model is revised when a new integration, data copy, or privilege changes the boundary; it is not a one-time drawing.

Worked examplefind the missing access path

Consider an order API where the customer endpoint checks ownership before returning an order. Assume a support console reads the same order store through a separate endpoint. The asset is the customer's order history. The first path is customer → API → ownership check → store; the second is support agent → console → support API → store. Protecting only the first path leaves the second path able to bypass customer checks. The design needs a support-specific permission, a reason for access where appropriate, and an audit event for the read. Check by testing both paths with an authorized user and an unauthorized user; the result must depend on the requested order and the caller's authority, not merely on a successful login.

§3 · Identity and access

Establish identity and enforce authorization

Definition

Authentication The process of establishing which principal is making a request.

Definition

Principal A user, service, or other entity whose identity can be used in an access decision.

Definition

Authorization The decision whether a principal may perform an action on a particular resource under the current conditions.

Definition

Least privilege Granting a principal only the permissions needed for its task, for only as long as needed.

Definition

Session token A credential presented with subsequent requests to associate them with an authenticated session.

An authenticated customer is not thereby authorized to read every order. The access decision must combine principal, action, and resource: “customer 12 may read order 86 because order 86 belongs to customer 12.” Checking only a role or trusting an order identifier supplied by the client leaves object-level access unprotected. Enforce the decision at a consistent server-side boundary on every relevant request, including administrative endpoints, background jobs, and alternate API paths. OWASP's Authorization Cheat Sheet recommends deny-by-default behavior and permission checks on each request.

For service-to-service calls, propagate identity only when a downstream service needs it and distinguish the calling service's authority from the end user's authority. Give a worker that sends receipts permission to read the fields it needs, not broad access to all customer records. If a permission decision depends on a remote policy service, define what happens when that service is unavailable; a timeout must not silently become permission to proceed.

Session design affects revocation and exposure. An opaque server-side session can be invalidated centrally; a signed self-contained token can be checked locally but may remain usable until expiry unless a revocation mechanism is added. Protect session credentials in transit and storage, set appropriate lifetimes, and rotate or revoke them after account compromise. A signed token is evidence of claims, not evidence that the request is authorized for every resource. Sensitive actions may require fresh authentication or an additional factor, according to their risk.

The diagram shows the decision sequence for one protected operation.

The target resource must be considered before the authorization decision. A policy that checks only whether the caller has an “order reader” role cannot distinguish the caller's order from another customer's order. The result should be tested for both permitted and forbidden resource identifiers.

§4 · Data protection

Protect data through its life cycle

Definition

Personal data Information relating to an identified or identifiable person, including data that can identify a person when combined with other available information.

Definition

Data minimization Collecting and retaining only the data needed for a specified purpose.

Definition

Retention policy A rule that states how long a category of data is kept, why, and what happens when that period ends.

Definition

Encryption in transit Protection of data while it moves between endpoints, commonly using Transport Layer Security (TLS).

Definition

Encryption at rest Protection of stored data by encrypting it with managed keys.

Definition

Key management The creation, storage, access control, rotation, and retirement of cryptographic keys.

Definition

Pseudonymous identifier A replacement identifier that does not directly name a person but may still be linkable to that person using other information.

For each data field, identify its purpose, the services that need it, every copy, and its deletion rule. A hosted payment flow, for example, can keep card details out of the shop's system altogether. A shipping address may be needed to fulfil an order but not in request logs or analytics events. Pseudonymous identifiers can support correlation without copying a full address, though they may still be personal data if re-identification remains possible. The ICO's data minimisation guidance expresses the principle as collecting data adequate and relevant to a purpose, and limited to what is necessary.

The data-life-cycle diagram makes secondary copies visible.

Read the branches as separate retention and access obligations. Deleting a row from the primary store does not automatically delete an export, a cache, a backup, or a log line. Some copies may need a different deletion method or a documented expiry; a requirement to erase data must name the systems in scope and the expected completion window. Legal and contractual retention requirements vary, so choose periods for the actual context rather than copying a generic number.

Definition

Password hashing A one-way, deliberately costly transformation used to verify a password without storing a recoverable copy of it.

Encryption in transit protects network hops, and encryption at rest protects stored copies in its threat model. Neither helps if an overprivileged service can ask for the plaintext or if the key is kept beside an accessible data export. Restrict key use, separate keys from data where feasible, and plan rotation and recovery before an incident. Passwords need password hashing rather than reversible encryption. OWASP's Cryptographic Storage Cheat Sheet describes these architectural distinctions.

Worked examplemake retention measurable

Consider a service that creates 10 million activity events each day. Assume each stored event occupies 250 bytes before indexes and replication, and assume the agreed retention period is 30 days. Daily logical growth is 10,000,000 × 250 = 2,500,000,000 bytes, or 2.5 GB using decimal units. A steady 30-day window holds 2.5 × 30 = 75 GB of logical event data. Keeping a full year instead would hold 2.5 × 365 = 912.5 GB; that is 912.5 ÷ 75 ≈ 12.17 times the 30-day window. Check: both figures use the same daily input and differ only in retained days. Indexes, replicas, and backups add storage, while the privacy requirement still needs a rule for each copy. The arithmetic makes an indefinite default visible as both a storage and exposure decision.

§5 · Abuse defenses

Validate input and limit abuse

Definition

Input validation Checking that received data has the expected form and satisfies the operation's business rules before it is used.

Definition

Injection An attack that causes untrusted input to be interpreted as a command or query structure rather than as data.

Definition

Rate limit A cap on the number of operations a caller may attempt in a defined period.

Definition

Quota A longer-term allowance for a caller's use of a resource, such as daily requests or stored bytes.

Definition

Parameterized query A database query in which untrusted values are passed as data separately from the query structure.

Definition

Output encoding Converting data for the context where it will be rendered so that it is not interpreted as executable markup or script.

Validate at the server boundary even when a client already validates. Types, lengths, ranges, and relationships between fields should match the operation. Validation does not replace context-specific defenses: use parameterized queries when untrusted values enter a database query, and encode output for the context in which it is rendered. A valid order identifier still requires an authorization check. OWASP's Input Validation Cheat Sheet separates these controls.

Abuse controls protect both users and shared capacity. Set limits around sign-in, password recovery, search, file upload, expensive exports, and external callbacks according to their different risks. Choose the key for each limit carefully: an IP address may group unrelated users, while an account-only limit may be bypassed before login. Apply limits at the relevant shared boundary and decide how clients learn that they have been limited. A limit based only on each server instance changes when the instance count changes.

Worked examplea per-instance limit that scales accidentally

Consider an API with four instances behind a load balancer and a stated per-caller limit of 100 requests per second. Assume each instance maintains its own independent counter and the caller's requests are spread evenly. Each instance can admit 100 requests per second, so the caller may get 4 × 100 = 400 requests/s accepted in total. Check: at 400 requests/s spread evenly, each instance sees 400 ÷ 4 = 100 requests/s and none exceeds its local limit. If the intended global allowance is 100 requests/s, the system needs a shared decision, consistent routing for that caller, or another design whose approximation is explicitly accepted. This example assumes even distribution; the exact observed maximum depends on routing and burst rules.

§6 · Audit and response

Make sensitive actions explainable

Definition

Audit log A protected record of security-relevant or privileged actions that captures who acted, what was affected, when, and the outcome, for a defined retention period.

Definition

Tamper evidence A property that makes unauthorized alteration or deletion of a record detectable, even if prevention fails.

Definition

Correlation identifier A reference carried across related requests and events so records about one operation can be joined without copying its sensitive contents.

An audit event for a refund, permission change, or sensitive export should identify the actor, action, target, outcome, and a correlation identifier. The log should be written on the path where the action is decided so that a successful privileged change is not invisible. Protect it with restricted write and read permissions, monitor whether event collection stops, and check for alteration. An audit log does not have to contain a copy of the affected personal record; storing a stable reference and the minimum needed context often provides accountability with less exposure.

The diagram shows the separation between a business action and its investigation record.

Read the two inputs to the audit event as the decision and the resulting action. The design must define what happens if audit recording fails for a sensitive change; silently succeeding can leave the system unable to explain that change. Ordinary diagnostic logs may have a different failure policy, but both kinds of log need sensitive-data filtering. Tokens, passwords, keys, and unnecessary personal data do not belong in logs. OWASP's Logging Cheat Sheet covers event selection, data exclusion, tamper detection, and log retention.

Security signals should lead to a response. Repeated denied access to many resources, sudden privilege changes, unusual exports, and failed key use can justify alerts, but thresholds need a known owner and an investigation path. Response planning should include revoking credentials, limiting an affected path, preserving evidence, and assessing which data copies may have been exposed.

§7 · Verification

Verify controls and revisit trade-offs

Definition

Security test A check that a stated protective rule holds under both permitted use and a representative misuse or failure.

Definition

Privacy risk The possibility that processing data about people causes harm even when a system is functioning as designed.

Definition

Replay Reuse of a previously valid request or message to trigger an action again when only one effect was intended.

Trace each material threat to a control and a test. For object-level authorization, try another user's identifier, an administrative path, and a background job. For retention, trace a test record through primary storage, caches, exports, logs, and backup expiry. For a lost secret, exercise rotation and revocation. For a payment or webhook integration, verify the sender and reject replay or unexpected state transitions. The tests should use the same boundaries shown in the threat model, including failure paths.

Security and privacy can pull in different directions. More detailed logs aid investigation but retain more information about people. Longer session lifetimes reduce login friction but extend the usefulness of a stolen credential. A remote authorization check can centralize policy but add a new availability dependency. State the affected user journey, the failure or misuse being prevented, and the cost of each option, then choose a rule that can be observed and revisited. NIST's Privacy Framework treats privacy risk across collection, use, storage, sharing, and disposition rather than as a property of storage alone.

· · Review

Common mistakes

Treating login as permission. An authenticated caller can still request another person's record or invoke an operation outside their role. This happens when an API checks identity once at the edge and assumes downstream paths are safe. Authorize the requested action on the specific resource at every relevant entry path, with deny-by-default behavior.

Encrypting everything while collecting too much. Encryption reduces some disclosure risks, but a service with legitimate decryption access can still misuse unnecessary fields. Collect data for an explicit purpose, constrain recipients, and apply a retention and deletion rule to every copy.

Adding an audit log without protecting it. A log that the same administrator can rewrite, or that contains raw tokens and personal records, can fail during an investigation and create another exposure path. Restrict access, make alteration detectable, filter sensitive values, and verify that required events are recorded.

Relying on input validation as the only boundary. A well-formed identifier can still target someone else's resource, and a well-formed string can still be dangerous in a query or rendered page. Validate shape and business rules, authorize separately, and use context-specific defenses such as parameterized queries and output encoding.

Applying a per-instance limit as a global promise. Local counters are simple, so a new server silently multiplies the caller's allowance. Define whether the target is per instance or across the fleet, then use a shared or deliberately approximate enforcement design and test it at the expected instance count.

· · Exercises

Practice questions

These questions mix recall, calculation, and application across the guide; each answer is collapsed beneath its question to be opened after working out an answer.

Question 1 · distinction

How can an encrypted customer database still violate a privacy requirement?

Answer

Encryption protects data against some unauthorized reads of stored copies. A system can still collect fields it does not need, use them for an undisclosed purpose, share them too broadly, or retain them beyond the agreed period. Privacy requirements govern those decisions even when storage is encrypted.

Question 2 · application

A signed-in customer can retrieve an order by changing the numeric identifier in the URL. Which check is missing, and where should it be enforced?

Answer

The API is missing authorization for the particular order. After authenticating the caller and loading the target order, the server should verify that the caller is permitted to read that order under the current policy. The same rule must cover other paths to the order, including exports and support tools where appropriate; changing the identifier to another customer's order should be denied.

Question 3 · calculation

A service creates 4 million personal-data events per day at an assumed 300 bytes per event before indexes and replicas. How much logical data does a 14-day retention window hold, and how much would a 90-day window hold?

Answer

Daily data is 4,000,000 × 300 = 1,200,000,000 bytes, or 1.2 GB in decimal units. Fourteen days hold 1.2 × 14 = 16.8 GB; 90 days hold 1.2 × 90 = 108 GB. Check: 108 ÷ 16.8 ≈ 6.43, matching 90 ÷ 14 ≈ 6.43. Copies, indexes, and backups add to both figures and need their own retention treatment.

Question 4 · misconception

Why is a 100-requests-per-second limiter on each of five API replicas not necessarily a 100-requests-per-second limit for one caller?

Answer

If each replica counts independently and requests are distributed evenly, each can admit 100 requests/s for the same caller. The fleet can then admit up to 5 × 100 = 500 requests/s. Check: at 500 requests/s evenly spread, each replica sees 100 requests/s. A global promise requires coordinated or caller-consistent enforcement, or an explicitly accepted approximation.

Question 5 · open-ended

An online shop adds a support export of customer orders and a third-party analytics service. Extend its threat model, access policy, privacy rules, audit design, and verification plan.

Answer

Add the support console, export store, transfer path, and analytics recipient to the flow diagram and mark the new trust boundaries. Define which support principals may export which orders, for what purpose, with what limits and review; require resource-level checks rather than a broad “support” login. Minimize or aggregate the fields sent to analytics and set retention and deletion rules for primary data, export files, downstream copies, and logs. Record who initiated an export, its scope, time, and outcome without logging the complete contents. Test unauthorized exports, overbroad fields, expired files, downstream deletion, credential revocation, and the audit trail for a completed export.

· · Finish

Review checklist

Without consulting notes, distinguish security from privacy; map assets, flows, and trust boundaries; define identity and resource-specific authorization; minimize data and plan protection, retention, and deletion across all copies; select validation and abuse controls; design protected audit events and useful alerts; and connect each important risk to a control and a test. A reader who can do all of these has covered the material.
